# Memory

Keep durable project knowledge here and under `memory/`. Before deep investigation, skim existing memory and reuse it.
If you had to figure out a stable fact or workflow during a run, add a concise memory entry before finishing so later runs do not rediscover it.

- Arise testing note: when validating invitation flow on the emulator, also check whether the contact has already been added in the vanilla Briar app installed on that emulator, because invite behavior may depend on that Briar-side contact state. Added 2026-03-19.
- On `emulator-5554`, a raw external invite can leave the preserved Arise invite task behind the official Briar task or launcher even though the invite task is still alive. Reopening the `Rise` recents card resumes that preserved task and keeps the invitation onboarding context intact through `SignInActivity` and back into `MainActivity`. Added 2026-03-19.
- See `memory/invite-link-environment.md` for the current device-role mapping: Arise stays on `emulator-5554`; the separate official Briar peer baseline is `emulator-5556`.
- On `emulator-5554`, Arise's Android share chooser exposes the full raw handshake link in the chooser preview itself under `android:id/content_preview_text`, so a `uiautomator dump` can recover the exact `briar://...` link without selecting a share target. Added 2026-03-20.
- On `emulator-5556`, `adb -s emulator-5556 shell am start -W -a android.intent.action.VIEW -d '<briar-link>' org.briarproject.briar.android` reopens official Briar's `AddContactActivity` with `linkInput` prefilled; continuing through nickname submission lands in `Pending Contact Requests`. Added 2026-03-20.
- On `emulator-5554`, warm Arise relaunches can preserve stale in-memory Briar runtime status (`hasDatabaseKey=true`, `hasIdentity=true`) inside the still-running process. For startup-auth/runtime diagnosis, force-stop first; the cold launch can differ materially and is the trustworthy signal. Added 2026-03-20.
- Upstream Briar's `AccountManager.hasDatabaseKey()` is process-local only: it becomes true only after `createAccount()` or `signIn()` in the current process and becomes false again after process exit. Use `accountExists()` to reason about encrypted key material on disk; do not treat cold-start `hasDatabaseKey=false` as proof that no Briar account exists. Added 2026-03-20.
- `agent-tools/test.sh` wraps the app module's `testDebugUnitTest` task. For focused JVM tests in library modules like `briar-runtime`, run the module task directly (for example `./gradlew :briar-runtime:test --tests com.example.rise.briar.runtime.BriarRuntimeManagerImplTest`). Added 2026-03-20.
- `SplashActivityViewModel.determineDestination()` runs before the transport bridge/runtime singleton has necessarily started, so cold-start auth routing cannot rely on runtime status alone unless splash explicitly probes the runtime first. Added 2026-03-20.
- `MainActivityViewModel.onStart()` can emit `LaunchSignIn` before a `repeatOnLifecycle(STARTED)` event collector becomes active on cold startup. For the signed-out invitation handoff, keep the `MainActivity` event collector active from `onCreate` so the initial sign-in launch is not lost and the app does not stall on a blank `MainActivity`. Added 2026-03-25.
