Staged Plan

  - Stage 0 – Flag Infrastructure (status: Firestore only)
      - Introduce a central feature toggle (e.g., BriarTransportMode) with three enum values: FIRESTORE, HYBRID, BRIAR_ONLY. Back it with a Koin-provided FeatureFlags service that reads from persistent prefs plus a debug override
  (and later remote config if needed). Default to FIRESTORE, expose a developer option to flip modes at runtime.
  - Stage 1 – Briar Runtime Shell (flag: HYBRID path unused)
      - Definition: a self-contained Gradle composite module (`briar-runtime`) that hosts the upstream Briar DI graph and exposes only Koin-registered bridge interfaces, letting us start/stop the Briar stack behind a feature flag without touching production app modules.
      - Wire Briar modules into a new Gradle composite (settings.gradle) but keep them out of the main variant by default; this introduces a self-contained `briar-runtime` module without forcing a broader app modularisation yet.
      - Implement a BriarComponentProvider that builds the Dagger component (mirroring BriarHeadlessApp) and exposes wrapped managers, yet never started when the flag is FIRESTORE.
      - Add a BriarRuntimeManager façade registered in Koin that lazily instantiates the Dagger graph, exposes only bridge interfaces (e.g., BriarChatGateway, BriarContactService), and handles lifecycle start/stop when the flag changes.
      - Provide a BriarComponentFactory binding so instrumentation and unit tests can supply fakes while production builds construct the real component.
      - Add diagnostics (logging + background service stub) to confirm the component initialises and shuts down safely under instrumentation without touching existing repositories.
  - Stage 2 – Chat Dual Stack (flag: HYBRID opt-in)
      - Extend ChatRepository and related ViewModels to branch on the flag: keep Firestore for FIRESTORE, route through a new BriarChatRepository when HYBRID.
      - Implement translation layers from Briar PrivateMessages to existing TextMessage models, using flows sourced from Briar’s event bus.
      - Persist a canonical chat timeline in the current local store, tagging entries with their transport source and original message identifiers so toggling modes preserves history and deduplication.
      - Provide migration helpers (e.g., UI switch in QA build) so testers can move between Firestore and Briar chat in one session.
      - Validate send/receive, account bootstrap, and contact sync via automated smoke tests under the flag.
  - Stage 3 – People & Presence (flag: HYBRID default)
      - Replace FirestorePeopleRepository with a dual implementation: Firestore remains for FIRESTORE, ContactManager wrapper for HYBRID/BRIAR_ONLY.
      - Audit other chat-adjacent flows (notifications, SnoozeService) to ensure they degrade gracefully when Briar is active.
      - Gather UX feedback on the Briar-backed experience while the legacy path is still available.
  - Stage 4 – Supporting Services (flag: transition to BRIAR_ONLY)
      - Rehome non-chat Firestore usages (alarms, FCM tokens, dashboard queries) either to Briar group messaging, local storage, or new sync primitives.
      - Once parity is achieved, flip the default flag to BRIAR_ONLY in internal builds while keeping the ability to fall back for emergency hotfixes.
  - Stage 5 – Cleanup (flag: BRIAR_ONLY shipped)
      - Remove Firebase/Firestore dependencies, google-services.json, and dead code paths.
      - Migrate data/credential storage to Briar’s account system exclusively, finalise documentation, and update licensing/attribution for GPL compliance.


More detailed Stage 0:
 - Define the toggle contract
      - Create BriarTransportMode enum (values FIRESTORE, HYBRID, BRIAR_ONLY) under a neutral package (e.g., app/src/main/java/com/example/rise/featureflags/).
      - Add an interface TransportModeProvider exposing the current mode plus observeMode(): Flow<BriarTransportMode> for reactive consumers.
  - Persist and initialise the flag
      - Back the provider with SharedPreferences (or DataStore if already in use) so the flag survives app restarts; default to FIRESTORE.
      - Seed preferences during app start (App.appModule) and register the provider with Koin so existing code can inject it.
  - Developer override controls
      - Add a debug-only settings screen entry or BuildConfig-gated dialog that lets testers switch modes at runtime; write changes through the provider.
      - Emit Timber logs whenever the mode flips, making QA verification easy.
      - Gate experimental connectors (e.g., Telegram login) behind dedicated debug flags so unfinished auth paths stay hidden from testers by default.
  - Integration touchpoints
      - Wrap Firestore-dependent repositories/services with a lightweight helper that reads the provider’s mode; for Stage 0 they should log loudly when the mode isn’t FIRESTORE so we can spot accidental toggles without breaking existing flows.
      - Introduce a TransportRuntimeBridge in Koin that owns the BriarRuntimeManager instance and exposes no-op stubs while the flag stays at FIRESTORE, easing later wiring without impacting current code paths.
      - Update instrumentation smoke tests to set the flag explicitly (ensures future stages can run side by side).
  - Documentation & tooling
      - Record flag behaviour and usage in agent-tools/ docs (e.g., a short how-to in QUICK_TEST_GUIDE.md) so testers know how to toggle it.
      - Optionally supply a shell helper (e.g., agent-tools/set_feature_flag.sh) that writes the preference via adb shell for CI/automation.
  - Verification checklist
      - Manual test: install debug build, confirm default mode is FIRESTORE, toggle to other values and observe persisted state/logs.
      - Unit test: small suite around TransportModeProvider ensuring default, persistence, and observer notifications work.
